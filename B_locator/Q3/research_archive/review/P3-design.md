## 0. 一页速览

| 项 | 结论 |

| 决策思想 | 把"下一步去哪测"变成全局网格上的标量场：**期望定位质量（越小越好）+ λ·距离**，取 argmin |

## 1. 策略流程（与题目给的设计思路一一对应）

```
/enter
 └─ 第 0 轮：原地（原点）依次检测 20 个频道                      ← 119 s，拿到若干"检测点+示向度"
 └─ 主循环
     ├─ 若存在"已定位两次(≥2 条方位且有界区域)"的频道 → 清理阶段（滚动时域动态规划）
     │    ├─ 每清一个目标就重读台账、以当前位置为起点、用最新区域中心重排航路
     │    │   （最近邻 + 2-opt），**途中新定位出来的频道立刻插队**
     │    ├─ 逐个：逼近区域中心（顺带测一条方位）→ 侧移精定位 → 覆盖式试探 /clear
     │    └─ 每个停点顺路补测未定位的频道（复用移动，节省时间）
     └─ 否则 / 清理结束 → 扫描阶段
          ├─ 把"还缺方位"的每个频道的方位按 (S,θ) 变换+插值叠加到全局网格
          ├─ 未覆盖/超阈值格子取 1500 m；归一化后叠加 λ·距离层
          ├─ 排除已访问扫描点邻域、离当前位置过近的格子
          └─ 取 argmin 作为下一个检测点 → 移动 → 新一轮扫描
```

**"未被覆盖 = 最大值"为什么有用**：E 越小定位越好，把没有信息的格子记成最差（1500 m），
它们只有在附近确实没有更好的格子时才会被选中 —— 这天然形成了"没信息时向外探索"的行为。

## 2. 决策场：把问题 2 的结果搬到任意检测点

### 2.1 刚体不变性

问题 2 的热力图是在"$S_1=(0,0)$、$\theta_1=0^\circ$"这一基准几何下算出的
$\mathbb E[D\mid\text{可检测}]$。$D$（交会区域直径）只依赖**距离与夹角**，因此把基准图
绕原点旋转 $\theta$、再平移到 $S$，就得到真实检测 $(S,\theta)$ 对应的场：

$$
b = R(-\theta)\,(g - S),\qquad E(g) = E_{\text{base}}(b)\quad(\text{双线性插值})
$$

自检 **T2** 验证了刚体不变性（最大绝对差 0），**T3** 验证插值落在邻域值域内。

### 2.2 必须按"先验外径 $t_{hi}$"分族（不做会错 2–4 倍）

基准图的源位先验是"沿示向度射线、$t\in[5,t_{hi}]$、权重 ∝ t"。其中

$$
t_{hi}(S,\theta)=\min\bigl(1500,\ \text{射线出靶区的距离}\bigr)
$$

**随检测点变化**：机器狗贴着靶区边界朝外测时，$t_{hi}$ 可能只有两三百米，而基准图用的是 1500 m。
实测（自检 T6b/T7）：固定用 1500 m 的图，边界朝外几何的相对误差中位数 **48.4%**、最大 **1120%**；
按 $t_{hi}$ 分族（9 个成员，查询时线性插值）后中位数 **0.26%**、P90 1.94%
（纯边界朝外几何的中位数 0.85%，仍比固定 $t_{hi}$ 好 **434 倍**）。

> 这一步是"变换 + 插值"能否成立的关键，也是本问与问题 2 的真正接口：
> **问题 2 给的是"给定一次检测后的期望定位质量"，问题 3 需要的是"把它搬到任意检测点"**。

生成方式（一次即可，9 个成员共约 13 s）：

```powershell
python src/p3_expect_field.py --build-family     # -> out/p3_family/p2_grid_map_thi*.csv
```

### 2.3 归一化 + 距离层

```python
E_k(g)  = clip( transform_and_interp(第 k 条方位), 0, 1500 )   # 未覆盖/超限 = 1500
E_norm  = mean_k( E_k ) / 1500                                  # "期望值的总和归一化"
score   = E_norm + λ · |g - p_robot| / (2·1800)                 # 距离项随距离线性增长
pick    = argmin score        （已访问点邻域与当前位置邻域被排除）
```

* 排除半径：已扫描点 250 m（重复扫描不产生新信息）、当前位置 60 m。
* 没有任何方位时退化为"最大最小距离"探索点（自检 S6）。
* 还可以叠加**探索项**（`field_discovery=True`）：对"没听到过"的频道，若候选点距其历史检测点
  都 < 450 m 就记 1500 —— 把扫描点推向真正能发现新源的地方。消融显示它与不加基本等价
  （40.7% vs 39.3%），默认关闭。

## 3. 定位与清除

### 3.1 定位区域（接问题 1）

每条频道维护"检测点 + 示向度"台账，用 `p1_intersection.analyse` 得到

* 有界多边形（顶点）、直径、**最小包围圆**（中心 + 半径 $r^*$）；
* 无界/退化/空集的状态（此时不清理，等下一次方位）。

由于题目保证示向度误差 $|e|\le 1^\circ$，**真源必落在所有 ±1° 楔的交集里**（自检 S5 用模拟器真值验证）。
若当前方位组合导致区域无界/退化，则退回"最近一次有界区域"（约束越多区域越小，故仍然包含真源）。

### 3.2 清除：覆盖式试探（**保证成功 —— 但仅在候选点不被截断时**）

* 清除半径 20 m；六边形试探格点间距 $34\ \text{m} \le 20\sqrt3 \approx 34.6$ m
  ⇒ 半径 $r$ 的圆域内任一点到某个试探点 ≤ 20 m（自检 S1 用 400 点/算例实测最大 19.42 m）。
* 有定位区域多边形时**只在"到多边形 ≤ 20 m"的格点上试**：交会区域常是细长四边形，
  用外接圆试探会浪费一倍以上的点。
* `r* > 60 m` 时先做一次**侧移精定位**：取与上一条视线近似正交方向、距离 $\approx 1.5r^*$ 的点再测一条
  —— 把交会角拉到 60–90°，$r^*$ 迅速下降（这是问题 1 "沿示向度方向逼近会退化"的正解）。
* 到达区域时顺带测一条方位（移动本来就要花，检测只多 6 s），常常直接得到 `near`（≤5 m）⇒ 立即清除。

#### 3.2.1 "已尝试"与"未尝试"必须分开记账（2026-09 修复）

`_probe_count`/`probe_points` 早期版本按"离中心由近及远"截断到 `probe_max_points=60`。
这有两个后果：

1. **覆盖保证被破坏**：截断丢掉的正是覆盖区域的**外圈**。实测 $r^* \ge 120$ m 就开始截断
   （$r^*=120$ m 需 61 个点，而 $r^*=200$ m 需 151 个）——偏偏代码在"区域里没找到目标"时
   还会把半径**扩大 1.6 倍**，正好落进被截断的区间。现默认 `probe_unlimited=True`
   取全部候选点，自检 **S9** 在 $r^*=195$ m 上实测最大覆盖距离 18.76 m，保证成立。
2. **失败归因被污染**：预算耗尽时 `sweep_clear` 里的 `can_afford` 会在**任何 `/clear` 发出之前**
   就返回，但旧代码照样 `clear_fail += 1` 并打印"本轮未清除成功"，读者会误以为
   "区域已铺满却没找到目标"。现在按三种结局分别记账（自检 **S10**）：

| 结局 | 含义 | 计数 |
|---|---|---|
| `SWEEP_OK` | 某点 `/clear` 成功 | 清除 +1 |
| `SWEEP_MISS` | 候选点**试遍**仍没打中 | `clear_fail += 1`（真失败） |
| `SWEEP_BUDGET` | 预算不足，**一个 `/clear` 都没发出** | `n_sweep_aborted += 1`，**不动** `clear_fail` |

命中/放弃都在日志里给出"候选 N 个 / 实际尝试 M 个"，不再用"N/N"冒充"已全部尝试"。
`SWEEP_BUDGET` 还会置 `abort_clear_phase` 让 `clear_phase` 立即收敛 ——
否则同一目标会被反复重规划（无此机制时 30 局重规划次数从 240 涨到 4919）。

**对指标的影响**：30 局演练清除率、逐局清除数、平均定位清除时间**完全不变**
（151/364、0.4148、223.1 s），程序运行时间 0.104 → 0.094 s/局。也就是说
这次修的是**记账与可复现性**，而不是策略行为；但它纠正了论文里"清除失败原因"
统计口径，并恢复了对大 $r^*$ 的覆盖保证。30 局里 `n_sweep_aborted` 合计 64
（中位数 2），`n_sweep_miss` 合计 **0** —— 即这 30 局中**没有任何一次**是
"候选点试遍仍没打中"，清除失败的归因从此清晰。

### 3.3 航路：滚动时域动态规划（每清一个目标就重新规划）

清理目标 = 各频道的**最新**定位区域中心。清理阶段不是"开始时排一次序、之后照着走"，
而是**滚动时域（rolling horizon）动态规划**：

```
while 还有可清理目标 且 时间够:
    ① 重读台账          # 途中新定位出来的频道立刻成为新目标
    ② 以当前位置为起点做 最近邻 + 2-opt 重新排序（用最新区域中心）
    ③ 只执行规划结果的第一个目标（逼近 → 侧移精定位 → 覆盖式试探清除）
    ④ 顺路补测（可能又新增可清理频道）
    → 回到 ①
```

三个实测得出的设计结论（都在消融表里）：

| 结论 | 数据（改正口径后，30 局） |
|---|---|
| **动态重规划不损失性能**：每步重规划 vs 阶段内固定顺序 | 清除率 0.9918 vs 0.9918、平均定位清除时间 397.8 vs 401.8 s；动态版换来的是"新定位目标立刻插队"的响应性（静态版恒为 0 次插队） |
| **按预算裁剪航路已无必要（也不再有害）**：目标执行是"边走边判"的（逼近/检测/逐点试探各自检查剩余时间、可随时中止） | 裁剪 0.9918 / 397.8 s vs 不裁剪 0.9918 / 397.8 s（完全同值 —— 因为清除阶段很少被预算卡住） |
| **"最大化预算内清除数"的一步前瞻（rollout+SPT）同样打平** | rollout 0.9918 / 396.7 s vs 全局航路结构 0.9918 / 397.8 s |
| 2-opt 相对纯最近邻：**差异在噪声内** | 0.9918 / 400.6 s vs 0.9918 / 397.8 s |
| **覆盖式试探必须保留**（只清中心会掉） | 0.9753 vs 0.9918 |
| **顺路补测有用** | 不顺路补测 0.9808 vs 0.9918 |
| **"新频道立刻补第二方位"要关掉**（破坏航路结构） | 开启 0.9780 / 426.3 s vs 关闭 0.9918 / 397.8 s |

> **读法**：改正口径后清除率已经贴近理论上界（0.99 vs 1.00），所以**航路结构类的优化全部打平** ——
> 动态/静态、裁剪/不裁剪、rollout/tour、2-opt/最近邻都不再有区分度。
> 真正有区分度的是"**要不要付信息获取的代价**"：覆盖式试探（保证一次成功）、
> 顺路补测（把移动的顺风车用在发现上）必须保留；而"为了早一点拿到第二方位就专门绕一趟"
> 是亏的。唯一的**参数级**收益是无信号重测间隔（450→1000 m，见 §5.1）。

> `clear_policy='tour'`（默认）/ `'rollout'`、`dynamic_replan`、`clear_budget_truncation`
> 都是可切换的配置项，便于复现上面的对照。

## 4. 接口层：把协议坑一次性处理掉

| 协议要求 | 实现 |
|---|---|
| 4 条指令、移动/切换频道无独立指令 | `HttpArena.measure/clear` 传入 position/channel，虚拟时间由模拟器返回 |
| 逐次串行、不得并发 | 全部同步阻塞调用，无并发 |
| 每个新动作新 `request_id`；重试复用原 ID 与原请求体 | `_new()` 生成 ID，`_post()` 在网络异常时用**同一 payload** 重试 |
| 同时校验 HTTP 状态与 `accepted` | HTTPError 也解析 JSON 体；只有 `accepted is True` 才更新本地状态 |
| `accepted=false` 时 `virtual_time_s=0` 不能当时间用 | 只用 accepted 响应更新 `virtual_time` |
| `/clear` 不切换频道 | 本地不改变 channel |
| `remaining_real_duration_s` 是动态的 | `remaining_budget_s()` = 进入时返回值 − 已用墙钟 − 安全余量 |
| 自己记录指令序列 | `HttpArena.log_path` 写 `protocol.jsonl`；`P3Robot.events` 写决策轨迹 |
| 日志 < 2 MB | 正常策略每局 40–60 次动作，日志几十 KB |

离线复刻（`MockArena`）与真实接口**逐字段同名**，因此策略代码在"演练"和"正式测试"上完全一致；
自检 A1 用附件 1 表 2 的算例逐条核对计时（105/111/194/199 s 全中）。

> （同一轮里后续试探点命中，因此不计作整轮失败）；`n_sweep_aborted = 0` 说明在 360000 s
> 口径下也没有"预算不足、一个 `/clear` 都没发出"的情形。详见 §3.2.1。

### 5.2 离线 41.5% 是怎么来的（口径错误的教训）

* 旧版 `MockArena` 默认 `budget_s=1200`，并且把它当**虚拟时钟上限**用：
  只要"已用虚拟时间 + 本步耗时 > 1200"就 `accepted=false`（超时拒动）。
* 于是一局最多只能跑完 1–2 轮扫描 + 3–4 次清除，虚拟时间停在 1185 s，
  报告出来的"程序运行时间预算用满"其实是**虚拟时钟被人为截断**。
* 真实模拟器（接口说明 1.4/4.5）的**虚拟世界限时是 360000 s（100 小时）**；
  1200 s 是 `/enter` 返回的 `remaining_real_duration_s`，指的是**现实时间**，
  并且由模拟器界面的 25 分钟窗口与 20 分钟程序时间共同约束，与虚拟时钟无关。
* 把 mock 的上限改成 360000 s 后（本次修正），同一批 30 局变成
  **清除率 0.992、平均 12.03 个、平均定位清除时间 397.8 s、行程 23 km**，
  与真实模拟器实测（10/10、642.9 s、22.2 km）同量级。
* **教训**：离线复刻的每一个"约束"都必须能在题目/接口说明里找到出处；
  凭空加一条约束会把结论带偏一个数量级，且因为离线看起来"自洽"而极难发现。
  唯一可靠的发现方式是**在真实模拟器上跑一次**。

### 5.4 真正的瓶颈：不知道自己已经清完了

两局在线实测暴露了同一个结构性问题：

| 局 | 全部清完的时刻 | 程序实际收工 | 清完后的空转 | 空转占比 |
|---|---|---|---|---|
| 第 1 局（10 个源） | 6428 s | 6914 s | 486 s | 7% |
| **第 2 局（14 个源）** | **3353 s** | 5286 s | **1932 s** | **37%** |

* 第 2 局的 14 个源在 3353 s 就全部清除完毕，但算法**无法确知"已经清完"**
  （题目只给"10–16 个"的范围，不清空靶区就不能排除残留源），于是继续扫到
  29 轮上限才收工，把平均定位清除时间从 239.5 s 抬到了 377.6 s（5286/14）。
* 第 1 局另有 3114 s（45%）花在"场上一条方位都没有"的**空场搜索**上
  （决策场 `E_norm ≡ 0`，score 只剩距离项，机器人在圆心附近 500 m 步长蹭点）。
* 试过在决策场里加"半径 1000 m 内未扫过的靶区比例"（几何覆盖层）：
  30 局随机清除率 0.407（vs 0.415 旧口径），外圈场景无差异 ⇒ **无稳定收益，已回滚**。

**改进方向（正式测试后）**：给"无信息阶段"一个**可证明完备**的扫掠判断 ——
按有效接收半径下界 1000 m 铺六边形格点（约 11 个停点即可覆盖半径 1800 m 的靶区），
扫完即可**确定性地宣称"靶区内不存在未清除源"**并提前 `/exit`。
这一步同时解决"空场乱蹭"和"清完了还在跑"两个问题，预计能把指标再降 30–50%；
另一个方向是利用问题 4 定向源的覆盖角信息（命中一次即可反推覆盖范围）。

### 5.3 预算分配：为什么"时间不够就别扫、直奔清除"是错的（2026-09 实测）

一个自然的想法是：既然扫描很贵，那就在剩余时间不够时**放弃扫描、直接按最优路线去清除**。
我们把它实现成可切换的策略并做了 60 局（同一批种子）配对对照 —— **全部变差或持平**：

| 变体 | 清除率 | 清除数 | 与 baseline 配对差 | 95% CI | 结论 |
|---|---|---|---|---|---|
| **A baseline（默认）** | **0.4021** | **5.100** | — | — | — |
| B 扫描闸门（扫完须够清最近目标） | 0.3995 | 5.067 | −0.033 | [−0.08, +0.01] | 持平 |
| C 扫描时间上限 50% 预算 | 0.3916 | 4.967 | −0.133 | [−0.24, −0.02] | **变差** |
| D 清理近点子集（可达性预筛） | 0.3876 | 4.917 | −0.183 | [−0.33, −0.04] | **变差** |
| E 贪心 + 剩余预算可达 | 0.3850 | 4.883 | −0.217 | [−0.37, −0.06] | **变差** |
| F 只用最近邻航路 | 0.3982 | 5.050 | −0.050 | [−0.19, +0.09] | 持平 |
| G 剩余预算裁剪航路 | 0.3863 | 4.900 | −0.200 | [−0.30, −0.10] | **变差** |
| H 闸门 + 贪心可达 | 0.3824 | 4.850 | −0.250 | [−0.41, −0.09] | **变差** |

**为什么这个直觉不成立**，三条实测证据：

1. **扫描与清除在主循环里本来就不怎么竞争。** 现行结构是"有可清目标就先清、清完才扫"，
   扫描只会发生在可清目标为空时。加闸门后，60 局里只有 **2 局**行为发生变化
   （`n_scan_gated` 平均 0.03 次/局），而这 2 局都因为少拿了某个频道的第二方位
   而少清了一个源 —— 净效果是 −0.033。
2. **"可达性"无法预判，因为代价估计是准的。** 对 242 次 `clear_target` 的校验
   （`review/out_cost_estimate.txt`）：成功清除时"实际/估计"中位数 **0.87**
   （P25 0.79 / P75 0.91），只有 5% 的实际耗时超过估计。也就是说
   `estimate_clear_cost` 不是乐观估计，而是**略偏悲观**；按它做"够不够"的判定
   并不能筛掉真正的浪费，反而会提前砍掉本来能清的目标。
3. **"已定位却没清"的目标大多是结构性不可达。** 末尾 49 个"已定位未清除"的目标中，
   26 个（53%）在刚变成可清目标时"剩余时间 ≥ 乐观耗时"，但其中大多数目标
   距离 540–1521 m（需 150–350 s 行程），而当时**同一时刻还有更近的目标排在航路第一位**；
   优化的正确方向不是"提前放弃远处的"，而是"别把近处的排在后面"
   （见 §5.4）。

> 这些开关（`scan_budget_gate` / `scan_budget_frac` / `clear_shortlist` /
> `clear_policy='tour_greedy_cost'`）都保留在 `P3Config` 里，默认全部关闭，
> 供论文的消融章节复现上表。**默认配置未做任何改动。**

### 5.4 天花板在哪：相对"已定位目标"上界的 78.7%

把问题拆成"发现"与"排序"两部分，可以定量看出还有多少空间：

* 对本局**实际曾经定位**（≥2 方位且有界区域）的目标，从原点出发用最近邻 + 2-opt
  在 1200 s 内最多能清 **6.483 个/局**（上界，见 `out_scan_gate_oracle.json`）；
* 策略实际清掉 **5.100 个/局** ⇒ 达到该上界的 **78.7%**。
* 也就是说，即使**完全不改进发现能力**，只把"对已定位目标的航路排序与取舍"做到最优，
  还有约 **1.38 个源/局**（≈ +11 个百分点清除率）的空间。

这 1.38 个的差距**不能**归因于下面三件事 —— 它们都已被 §5.5 的实测排除：

| 候选解释 | 实测结论 |
|---|---|
| 定位区域中心估不准 ⇒ 走错地方 | 中心到真源**中位数 5.5 m**；换成真源位置只多清 6 个源（+1.7pt），折算上界贡献 ≈ +0.2 个/局 |
| 排序用了"过期"的中心 | 决策→执行的中心漂移 **恒为 0.0 m**（470/470，自检 S11） |
| 2-opt 改写了第一步（滚动时域只看第一步） | `nn2opt_keepfirst` 与纯 `nn` **逐位相同**（均 303 个）；无 2-opt 反而掉 0.6pt |

**剩下的差距更可能来自"在线信息结构"本身**：本节上界假设"一次性掌握全部已定位目标、
从原点出发走最优航路"，而真实策略是**边走边发现、每步重排**，且不少目标的区域中心
在"刚被发现"时就已经远离起点。要判断这 1.38 个里还有多少真能拿到，下一步应把上界
改成**在线可达上界**：固定每个目标的"发现时刻 + 当时机器狗位置"，再在其上求最优航路。

### 5.5 区域中心估计的质量，与"滚动排序错位"的排查

§5.4 指出真正的空间在"已定位目标的排序与取舍"。于是先量化两个可能的病灶。

**(a) 区域中心估计有多准（30 局 / 370 个样本，`review/out_center_quality.txt`）**

| 量 | 值 |
|---|---|
| 中心到**真源**距离 | 均值 25.0 m，**中位数 5.5 m**，P90 32.8 m |
| 最小包围圆半径 $r^*$ | 均值 73.6 m，中位数 38.2 m |
| 距离 / $r^*$ | 中位数 0.19，P90 0.47 |
| 真源落在最小包围圆内 | **370/370 = 100%** |

中心只在**拿到新方位**时更新（2→3 条方位漂移均值 25.0 m，无新方位时漂移恒为 0）。
它的用处有三处：① 航路排序的距离键；② `clear_target` 的逼近目标点；③ 覆盖式试探的中心。
其中 ② 最关键 —— 清除半径只有 20 m，而中心误差中位数 5.5 m，所以**"逼近到中心 + 测一条方位"
通常直接命中**（实测清除点到真源：中位数 3.2 m、P90 9.2 m），覆盖式试探只是保险。

**对照实验**（只把 `bounded_region` 返回的中心换成真源位置，其余策略逐字不变）：
清除 151 → **157**（5.033 → 5.233 个/局，配对差 +0.200，SE 0.074，胜/平/负 6/24/0）。
⇒ **中心估计误差的总代价只有 6 个源（+1.7pt）**，远小于 §5.4 的 1.38 个/局（+11pt）。
另外比较了三种中心定义（最小包围圆中心 / 顶点质心 / 面积质心），中位数误差
6.85 / 8.03 / 7.72 m —— **几乎无差别**。原因是误差来源是 ±1° 的示向度不确定性本身
（1000 m 处约 17 m 横向误差），换中心定义只是在同一个不确定球内换个点。

**(b) 滚动排序会不会用到"过期的中心"（60 局 / 822 次排序、470 次执行）**

结论：**完全不会**。排序决策时刻的中心与执行时刻的中心，漂移量
**均值/中位数/P90/最大全部 = 0.0 m**（470/470）。原因是新方位只在 `/measure` 之后产生，
而一次 `clear_target` 期间的逼近检测发生在**决策之后**，所以排序依据在执行时依然有效。
（新增自检 **S11** 把这一性质钉住。）

**(c) 只有第一步重要，那 2-opt 改写第一步有害吗**

滚动时域下每步只执行第一个目标，所以"总路程最短"并非正确的目标函数。
实测 2-opt 确实会改写第一步：**14.1%（82/580）** 的排序其第一步不是最近的目标。
于是加了 `tour='nn2opt_keepfirst'`（钉住最近点作第一步，只对后续子序列做 2-opt）做 60 局对照：

| 变体 | 清除率 | 清除数 | 与 nn2opt 配对差 | 95% CI |
|---|---|---|---|---|
| **nn2opt（默认）** | **0.4021** | **306** | — | — |
| nn2opt_keepfirst | 0.3982 | 303 | −0.050 | [−0.19, +0.09] |
| nn（纯最近邻） | 0.3982 | 303 | −0.050 | [−0.19, +0.09] |

`keepfirst` 与纯 `nn` **逐位相同**（都是 303）——说明被 2-opt 改掉第一步的那些情形里，
改与不改的后续收益正好抵消。**默认仍是 nn2opt**（无 2-opt 掉 0.6pt，自检 S12 确认
2-opt 把 5 个目标的航路从 7030 m 压到 5577 m 且本例第一步不变）。

> 小结：§5.4 的 +1.38 个/局**不能**由"中心估计误差"或"排序依据过期"解释
> （两者合计上限约 +0.2）。剩下的差距更可能来自**在线信息结构本身**：
> 上界假设"一次性掌握全部已定位目标、从原点出发最优航路"，而实际策略是
> 边走边发现、每步重排，且部分目标的区域中心在发现时就已远离起点。
> 下一步应把上界改成**在线可达上界**（限定"发现时刻 + 当时位置"），才能判断
> 这 1.38 个里还有多少是真能拿到的。

## 7. 已知边界与后续（问题 4 的接口）

1. **定向源**：`MockArena.MockSource` 已支持 `cone_half`/`dir_deg`；`no_signal` 的三种原因
   （无该频道 / 超接收半径 / 不在覆盖角内）在 `P3Robot` 里目前统一按"没听到"处理，
   问题 4 需要加"同一点换方向排除"的诊断逻辑。
2. **发现能力**：当前"探索"由"未覆盖 = 1500 m"与顺路补测承担，等价于被动探索；
   几何覆盖层（"1000 m 内未扫过的靶区比例"）实测无稳定收益，已回滚；
   若要做主动探索，建议改成"无信息阶段触发一次显式 1000 m 六边形系统扫掠"。
3. **清除失败重试**：`clear_fail` 标记后需等新方位才会再试；若正式测试中出现大面积失败，
   应放宽 `clear_max_radius_m` 或增加覆盖半径倍数（第 4 步已实现一次 1.6 倍扩大）。
   注意"预算不足放弃"（`SWEEP_BUDGET`）**不**置 `clear_fail`，因此剩余时间够时会在
   后续阶段重试——这与"试遍没打中"（`SWEEP_MISS`）是两种不同的处置。
4. **正式测试**：实测一局 182–396 次动作、日志 40–80 KB（远小于 2 MB 限制）、
   墙钟 2.7–6.5 s（现实预算 1200 s）；程序运行时间以 `remaining_real_duration_s` 为准，
   策略在剩余时间不足时自动降级（缩短扫描轮、收工退出）。
   两局演练均 100% 清除（10/10、14/14）。正式测试 3 次之间**不要改代码**，
   否则表 1 的三次结果不可比；每局结束后从模拟器导出行为日志（`.jlog`，不要改文件名）放入支撑材料。
5. **覆盖式试探的点数**：默认 `probe_unlimited=True`，$r^*=200$ m 时单次试探最多 151 个候选点，
   按间距折算约 200 s 虚拟行程。所以"保证成功"是**条件保证**：只要还有预算走完候选点就一定命中。
   在 1200 s 旧口径下预算常常在走完之前就耗尽（消融表里"覆盖式试探按点数封顶 60（破坏覆盖保证）"
   一行即为该对照）；修正到 360000 s 口径后，主要代价变成**墙钟与动作次数**，而不是虚拟时间。
6. **未覆盖的逻辑分支**：`MockArena.measure` 把"距离超接收半径"和"频道不存在"统一返回
   `no_signal`（`p3_arena.py:227`）。本分支已把 `nosignal_gap_m` 默认值从 450 m 提到
   **1000 m**（= 有效接收半径下界；实测检测次数 289→186、平均定位清除 398→315 s），
   但仍**不能只靠 mock 定死**：真机有效接收半径 1000–1500 m，合理间隔应显著更大，
   正式测试前必须用真实模拟器复核。这也是问题 4 定向源诊断的入口。
